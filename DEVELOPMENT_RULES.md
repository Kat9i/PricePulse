# PricePulse — Development Rules

Эти правила читаются **перед** началом работы над кодом. Цель — единый стиль, предсказуемая история изменений и отсутствие проблем с секретами.

---

## 1. Стиль кода

### Язык
- **Комментарии и docstring** — на русском
- **Имена переменных, функций, классов, файлов** — на английском

### Именование файлов
| Что | Стиль | Пример |
|-----|-------|--------|
| Python-модули | `snake_case` | `price_checker.py` |
| Папки | `snake_case` | `parsers/`, `api/routers/` |
| Миграции Alembic | авто-генерация | `0001_create_users.py` |
| Конфиги | `snake_case` | `.env.example` |

### Именование в коде Python
| Что | Стиль | Пример |
|-----|-------|--------|
| Переменные и функции | `snake_case` | `current_min_price`, `get_trackings()` |
| Классы | `PascalCase` | `User`, `TrackingCreate` |
| Константы | `UPPER_SNAKE_CASE` | `MAX_FREE_TRACKINGS = 10` |
| SQLAlchemy-модели | `PascalCase` | `class Product(Base)` |
| Pydantic-схемы | `PascalCase` + суффикс | `UserResponse`, `TrackingCreate` |
| Роутеры (файлы) | `snake_case`, множ. число | `trackings.py`, `users.py` |
| Enum-значения | `snake_case`-строки | `"active"`, `"price_reached"` |

### Форматирование
- Максимальная длина строки: **100 символов**
- Форматтер: **black** (запускать перед коммитом)
- Линтер: **ruff**
- Импорты: сортировка через **isort** (входит в ruff)

### Pydantic-схемы vs ORM-модели
- SQLAlchemy-модели живут в `db/models.py` — только описание таблиц
- Pydantic-схемы живут в `api/schemas/` — только описание запросов и ответов
- Никогда не возвращать ORM-объект напрямую из роутера

## 2. Формат коммитов

Используем [Conventional Commits](https://www.conventionalcommits.org/).

### Структура
```
<type>(<scope>): <описание на русском>

[опциональное тело]
[опциональный футер]
```

### Типы
| Тип | Когда использовать |
|-----|--------------------|
| `feat` | Новая функциональность |
| `fix` | Исправление бага |
| `docs` | Изменения в документации (md-файлы, docstring) |
| `refactor` | Рефакторинг без изменения поведения |
| `test` | Добавление или исправление тестов |
| `chore` | Инфраструктура: зависимости, Docker, CI |
| `db` | Миграции базы данных |
| `parser` | Изменения в парсерах WB/Ozon |
| `style` | Форматирование, отступы (без логики) |

### Scope (необязательно, уточняет область)
`api`, `worker`, `parser`, `db`, `bot`, `payments`, `auth`

### Примеры
```
feat(api): добавить эндпоинт удаления отслеживания
fix(parser): исправить парсинг цены WB при отсутствии остатков
db: добавить миграцию уникального индекса seller
chore: обновить зависимости до актуальных версий
docs: обновить ARCHITECTURE.md — исправить расхождения с брифом
test(api): добавить тест POST /trackings с превышением лимита
parser(wb): добавить fallback на Playwright при 403
```

## 3. Changelog

При каждом значимом изменении обновляй `CHANGELOG.md` **в том же коммите**.

### Что считается значимым
- Новый API-эндпоинт
- Изменение структуры БД (миграция)
- Новая интеграция с внешним сервисом
- Изменение бизнес-логики (лимиты, тарифы, условия уведомлений)
- Исправление бага, влияющего на пользователя

### Что не нужно фиксировать
- Форматирование кода
- Переименование переменных
- Обновление зависимостей без изменения поведения

### Формат записи
```markdown
## [0.2.0] - 2026-06-01
### Added
- POST /trackings — добавление товара в отслеживание

### Changed
- Таблица seller: добавлен UNIQUE (product_id, seller_name)

### Fixed
- Исправлен дублирующийся INSERT продавцов при повторном парсинге
```

Формат основан на [Keep a Changelog](https://keepachangelog.com/en/1.0.0/).

## 4. Секреты

**Правило одно: секреты только в `.env`, никогда в код.**

### Что считается секретом
- Токен Telegram-бота (`BOT_TOKEN`)
- Ключи ЮКасса (`YUKASSA_SECRET_KEY`, `YUKASSA_SHOP_ID`)
- `SECRET_KEY` для подписи JWT
- `DATABASE_URL` (содержит пароль)
- Прокси с логином/паролем

### Обязательно
- `.env` добавлен в `.gitignore` — никогда не коммитить
- Все секреты читаются через `pydantic-settings` в `core/config.py`
- В коде нет строк вида `token = "7123456789:AAF..."` или `password = "qwerty"`

### Проверка перед коммитом
Запустить `git diff --staged` и убедиться что нет строк с токенами или паролями.

## 5. .env.example

`.env.example` — публичный шаблон со всеми переменными без реальных значений. Обновляется **сразу** при добавлении новой переменной окружения.

### Текущий шаблон
```dotenv
# База данных
DATABASE_URL=postgresql+asyncpg://user:password@localhost:5432/pricepulse

# Telegram
BOT_TOKEN=your_telegram_bot_token_here
WEBHOOK_URL=https://yourdomain.com

# JWT
SECRET_KEY=your_secret_key_here_min_32_chars

# ЮКасса
YUKASSA_SHOP_ID=your_shop_id
YUKASSA_SECRET_KEY=your_secret_key

# Прокси (через запятую)
PROXY_LIST=http://user:pass@host:port,http://user:pass@host2:port2

# Playwright
PLAYWRIGHT_HEADLESS=true
```

### Правило
Добавил переменную в `config.py` → сразу добавил строку в `.env.example` → упомянул в коммите.

## 6. Порядок работы

Перед тем как писать код — читать документацию. Всегда.

### Обязательный checklist перед стартом задачи
```
[ ] Прочитать ARCHITECTURE.md — убедиться что задача вписывается в архитектуру
[ ] Прочитать DEVELOPMENT_RULES.md — этот файл
[ ] Если задача меняет API — обновить раздел API в ARCHITECTURE.md
[ ] Если задача меняет схему БД — написать миграцию Alembic
[ ] После выполнения — обновить CHANGELOG.md
```

### Где что живёт (шпаргалка)
| Что делаю | Куда смотреть |
|-----------|--------------|
| Добавляю эндпоинт | `api/routers/`, `api/schemas/` |
| Меняю бизнес-логику | `services/` |
| Меняю парсер | `parsers/wb.py` или `parsers/ozon.py` |
| Меняю логику воркера | `worker/price_checker.py` |
| Меняю таблицу | `db/models.py` + новая миграция в `db/migrations/versions/` |
| Добавляю уведомление | `worker/notifier.py` |
| Добавляю переменную окружения | `core/config.py` + `.env.example` |

## 7. Тесты

При добавлении нового API-действия — писать минимальный тест.

### Расположение
```
tests/
├── conftest.py          # фикстуры: тестовый клиент, тестовая БД, мок-пользователь
├── test_auth.py
├── test_trackings.py
├── test_users.py
└── test_webhooks.py
```

### Минимальный тест для нового эндпоинта
Для каждого нового эндпоинта нужно покрыть:
1. **Happy path** — нормальный запрос возвращает ожидаемый ответ
2. **Auth guard** — запрос без токена возвращает `401`
3. **Граничный случай** — если есть лимит или условие (например, лимит 10 товаров) — тест на его нарушение

### Пример именования тестов
```python
def test_add_tracking_success():         # happy path
def test_add_tracking_unauthorized():    # без токена → 401
def test_add_tracking_limit_exceeded():  # 11-й товар на free → 403
def test_delete_tracking_not_found():    # удалить чужой/несуществующий → 404
```

### Запуск
```bash
pytest tests/ -v
```

### Что НЕ нужно тестировать в MVP
- Парсеры WB/Ozon (нестабильные внешние сервисы — мокировать слишком дорого)
- Отправку Telegram-уведомлений (интеграционный тест, не unit)
